4. Radical MaxManager transformation

This is the most important part.

Do not simply copy features from the reference applications and add them to the existing interface.

I want you to reconsider MaxManager as a complete product.

First audit the current repository and identify:

- Existing architecture.
- Core modules.
- Existing features.
- Duplicated or obsolete implementations.
- Performance bottlenecks.
- Background processes.
- Memory consumption.
- Battery consumption.
- UI inconsistencies.
- Security weaknesses.
- Technical debt.
- Unfinished features.
- Compatibility problems.

Then develop a new architecture and product direction.

Architectural objectives

Build a clean, modular, maintainable architecture with clear separation between:

1. Hardware information and monitoring.
2. Device capability detection.
3. Kernel and system control.
4. Performance management.
5. Battery optimization.
6. Thermal safety.
7. Per-app profiles.
8. Automation.
9. Root and privileged execution.
10. Diagnostics and system health.
11. User interface and settings.
12. Configuration and persistence.

Use a modular architecture that is appropriate for Android. Avoid unnecessary abstraction and overengineering.

Each module must have a clear responsibility and a documented interface.

New device intelligence system

Develop a reliable device information layer that can identify:

- SoC and chipset.
- CPU architecture and cores.
- CPU frequencies and governors.
- GPU and supported frequencies.
- RAM and memory configuration.
- Battery information.
- Thermal sensors.
- Display capabilities.
- Storage devices and partitions.
- Kernel version and build information.
- Android version and security patch.
- Available system interfaces.

Every value should have a known source and confidence level.

Never fabricate hardware information or display misleading values when an interface is unavailable.

New monitoring system

Develop efficient hardware monitoring with:

- Accurate readings.
- Adaptive sampling intervals.
- Event-driven updates where possible.
- No unnecessary polling.
- No permanent high-frequency monitoring.
- No unnecessary wake locks.
- Minimal CPU and RAM consumption.
- Correct lifecycle management.

Monitoring should primarily operate when the relevant screen or feature is active.

The application must have near-zero idle impact.

New performance and battery engine

Reconsider the existing optimization mechanisms.

Build a system that understands the difference between:

- Actual device capabilities.
- Available kernel controls.
- Read-only information.
- Writable interfaces.
- Unsupported controls.
- Device-specific implementations.

Do not assume every Android device supports the same kernel parameters.

Support appropriate root and non-root execution paths, and use Shizuku or other privileged mechanisms only where technically justified.

Safety and control architecture

Preserve and strengthen the existing MaxManager safety principles.

The priority must remain:

SAFETY > APP PROFILE > MAX AI > MANUAL

All system modifications must pass through a single controlled write mechanism.

Use:

1. Read current value.
2. Validate the requested change.
3. Check device and kernel compatibility.
4. Apply the change.
5. Read back the actual value.
6. Confirm whether the change succeeded.
7. Roll back when verification fails.

Do not report success merely because a command returned exit code zero.

Never modify dangerous thermal protections, watchdog mechanisms, power safety interfaces, or unknown system-critical nodes.

Unsupported controls must remain unavailable rather than being presented as functional.
