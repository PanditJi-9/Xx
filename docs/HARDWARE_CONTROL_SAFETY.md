# HARDWARE_CONTROL_SAFETY — عقد التحكّم بالعتاد

> مخرج المرحلة 4، وأخطر ملف فيها: كل ما يمسّ sysfs/الحرارة/الترددات. مأخوذ من الخطوط الحمراء
> الملزمة (لا كتابة من `ui/**`، وكل الكتابات عبر الـarbiter، ولا `status_unknown` مُصنَّع) ومربوط
> بما قيس من أسطح الأداء في الأصل، **لا** بما تفعله خدمات Nubia داخليًّا (غير مقروءة، تبقى `UNVERIFIED`).

---

## 1. نطاق هذا العقد

| داخل النطاق | خارج النطاق (ولا يُدَّعى) |
| --- | --- |
| قراءة/كتابة ترددات وسياسات CPU/GPU عبر ملفات sysfs القياسية | أي مسار خاص بـNubia/ZTE لم يُقَس |
| قراءة الحرارة/البطارية | تعديل حماية حرارية للنظام |
| تفعيل/تعطيل حكّام (governor) موجودة | تثبيت وحدات نواة أو تعديلها |
| أولويات العمليات (nice/cgroup) إن توفّرت | root دائم أو تعديل SELinux |
| إحصاء استخدام (CPU/ذاكرة) للعرض | تتبّع شبكة/بيانات المستخدم |

**SELinux لا يُلمس.** أي `setenforce 0` أو `supolicy` أو تعديل سياق ممنوع مطلقًا: تغيير سياسة النظام
ليس «ميزة أداء»، وهو خارج ما يمكن اختباره بأمان على جهاز المالك.

---

## 2. المسارات المعروفة والكشف

| القدرة | مسار/واجهة | كشفها |
| --- | --- | --- |
| `scaling_max_freq`/`min_freq` | `/sys/devices/system/cpu/cpuN/cpufreq/*` | قراءة ناجحة + وجود `policy0` أو `cpu0` |
| `scaling_governor` | نفس المجلد | قراءة القيمة الحالية ومقارنتها بنطاق `scaling_available_governors` |
| GPU (Adreno) | `/sys/class/kgsl/kgsl-3d0/*` | قراءة `max_gpuclk`/`gpu_clock` |
| GPU (Mali/generic) | `/sys/class/devfreq/*` | وجود `devfreq` قابل للقراءة |
| حرارة | `BatteryManager.EXTRA_TEMPERATURE` أو `/sys/class/thermal/thermal_zone*/temp` | أول مصدر يُرجع قيمة معقولة (مدى مفحوص) |
| أولوية | `Process.setThreadPriority` / cgroup | مدعوم على كل Android ⇒ `AVAILABLE` بلا كتابة |

**قاعدة الكشف:** وجود المسار **ليس** دليلًا على قابلية الكتابة. القدرة `AVAILABLE` فقط بعد
**كتابة تجريبية بالقيمة الحالية نفسها** (كتابة بلا تغيير فعلي) وقراءة مؤكِّدة. أي فشل ⇒
`UNSUPPORTED` مع `errno`/نصّ الاستثناء حرفيًّا.

---

## 3. قواعد الكتابة (ست قواعد لا استثناء)

1. **قراءة قبل كل كتابة**، وحفظ القيمة الأصلية في `ClaimToken`.
2. **استعادة عند `release`** — نهاية الجلسة أو خروج التطبيق تعيد ما كان. الاستعادة ليست تحسينًا.
3. **مدى معقول** من `scaling_available_frequencies`: لا قيمة مخترعة، ولا `max` فوق ما يعلنه النظام.
4. **تسلسل CPU→GPU→الحرارة**: لا رفع ترددات بعد قراءة حرارة فوق حدّ السلامة.
5. **سقف حرارة `SAFETY`**: عند تجاوز الحدّ (اختيار افتراضي: 45°C للبطارية) تُلغى كل الطلبات
   غير الآمنة ويُعاد الحكّم الأصلي، ويُبلَّغ المستخدم بالسبب.
6. **لا كتابة متزامنة**: arbiter يملك المسار؛ طلب ثانٍ يُرفض بـ`ARBITER_DENIED` ويُسمّى المالك الحالي.

---

## 4. التقليل والرجوع (Fail-safe)

| الحالة | السلوك |
| --- | --- |
| فشل الكتابة (SELinux/صلاحية) | `UNSUPPORTED` + السبب، ولا إعادة محاولة في الجلسة |
| انقطاع الاتصال بمالك العتاد | المستهلك يعلن `UNKNOWN` ويعيد المحاولة عند حدث (لا في حلقة) |
| انهيار عملية قادمة أثناء ملكية | استعادة عند إعادة التشغيل: لا حالة محفوظة «مملوكة» تُستعاد آليًّا |
| إعادة تشغيل الجهاز | كل شيء يعود لإعدادات النظام؛ لا خدمة إقلاع تعدّل الترددات |
| جهاز بلا sysfs قابل للقراءة | كل عائلة الأداء `UNSUPPORTED` — وتُعرض واجهة بالسبب، لا أزرار ميتة |

---

## 5. الصدق في العرض (لا تليمتري مُصنَّع)

- كل رقم معروض يحمل **مصدره ووقته**: `source=<path|api> at=<time>`.
- قيمة غير محدّثة ⇒ تُعلَّم بأنها قديمة؛ لا تُعرض كأنها حيّة.
- `status_unknown` قيمة مشروعة، ولا تُستبدل بـ`0`.
- لا «نسبة أداء» محسوبة من أرقام غير مقيسة؛ النِسَب تحتاج خطّ أساس مقيس على الجهاز نفسه.

---

## 6. ما يحتاج جهازًا (ولا يُدَّعى الآن)

- أي `AVAILABLE` على أي جهاز: **صفر قياس** حتى الآن.
- سلوك الحرارة الحقيقي تحت حمل، واستقرار `scaling_max_freq` على SoC مختلفة.
- تعارض مسارات Nubia/ZTE مع مساراتنا (الأصل قد يستخدم مسارًا مختلفًا — غير مقيس، `UNVERIFIED`).
- الحكم النهائي: **يحتاج جهازًا**، ولا يُغني عنه بناء CI ناجح.
